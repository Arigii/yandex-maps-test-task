# Тестовое задание: интеграция с Яндекс.Картами

Laravel 11 (API + Sanctum) + Vue 3 (Composition API, Vite, Pinia).

## Структура репозитория

```
backend/    Laravel API (Sanctum, очереди, парсер)
frontend/   Vue 3 SPA (Vite)
docker/     nginx конфиг
docker-compose.yml
```

## Как поднять локально

### Вариант 1 — Docker (рекомендуется)

```bash
git clone <repo> && cd <repo>

# 1. Собрать полноценный Laravel-скелет и наложить на него код из backend/
composer create-project laravel/laravel backend-skeleton
rsync -a backend-skeleton/ backend/ --exclude=app --exclude=database --exclude=routes --exclude=bootstrap
rm -rf backend-skeleton

cp backend/.env.example backend/.env
docker compose up -d --build

docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate --seed
```

Backend: http://localhost:8000, Frontend: http://localhost:5173.
Логин из сида: `demo@example.com` / `demo12345` (переопределяется в `.env`).

### Вариант 2 — без Docker

```bash
composer create-project laravel/laravel backend-skeleton
rsync -a backend-skeleton/ backend/ --exclude=app --exclude=database --exclude=routes --exclude=bootstrap
cd backend && cp .env.example .env
composer install && php artisan key:generate
# настроить DB_* на локальный MySQL/Postgres, QUEUE_CONNECTION=redis или database
php artisan migrate --seed
php artisan queue:work --queue=parsing &
php artisan serve

cd ../frontend && npm install && npm run dev
```

### Переменные окружения (backend/.env)

| Переменная | Смысл |
|---|---|
| `YANDEX_PARSER_STRATEGY` | `http_json` (по умолчанию) или `playwright` |
| `YANDEX_PARSER_USE_MOCK` | `true` — фикстуры вместо реального Яндекса (для демо/CI) |
| `YANDEX_REQUEST_DELAY_MS` | пауза между запросами к источнику одним воркером |
| `YANDEX_PROXY_POOL` | список прокси через запятую |
| `YANDEX_USER_AGENT_POOL` | список User-Agent через `|` |
| `SANCTUM_STATEFUL_DOMAINS`, `FRONTEND_URL` | для корректной работы SPA-cookie-аутентификации |

## Как работает приложение

1. **Вход** — `POST /api/login`, Sanctum SPA (cookie-based), сид-пользователь без регистрации.
2. **Настройки** — вставка ссылки на карточку → `UrlValidator` вытаскивает `oid`
   организации → создаётся/обновляется запись `organizations` → в очередь
   `parsing` ставится `ParseOrganizationReviewsJob`.
3. Фронт поллит `GET /organizations/{id}/status` раз в 2 сек и показывает
   прогресс-бар, пока `status` не станет `done`/`failed`/`structure_changed`.
4. **Отзывы** отдаются пагинированно (`GET /organizations/{id}/reviews?page=N`,
   50 на страницу) **из БД**, а не из живого источника — см. пункт ниже.

## Архитектура парсинга

```
Controller → dispatch(ParseOrganizationReviewsJob)
                     │
                     ▼
        OrganizationParser (оркестрация: агрегаты + все страницы отзывов)
                     │
                     ▼
     OrganizationFetcherInterface  ← выбирается в YandexParserServiceProvider
        ├── HttpJsonFetcher   (прод-стратегия по умолчанию)
        ├── PlaywrightFetcher (fallback, каркас)
        └── MockFetcher       (для демо/CI, включён сейчас)
                     │
                     ▼
        OrganizationSyncService (идемпотентный upsert + снапшоты)
```

Разделение **fetch** (сходить и получить сырые данные) и **extract**
(превратить их в `ParsedOrganization`/`ParsedReview`) сделано намеренно:
при смене вёрстки/API Яндекса ломается предсказуемо — либо на уровне
конкретного фетчера, либо на уровне разбора конкретного поля, а не «где-то
в середине большого метода».

## Обоснование подхода к парсингу

**Выбор: разбор внутренних JSON-запросов карточки (`HttpJsonFetcher`), с
headless-браузером (`PlaywrightFetcher`) как fallback-стратегией за тем же
интерфейсом.**

| | Внутренние JSON-запросы | Headless-браузер (Playwright) |
|---|---|---|
| Скорость | Высокая — сотни запросов в минуту при разумном троттлинге | На порядок медленнее: рендер страницы, JS, ожидания |
| Ресурсы | Лёгкий HTTP-клиент, дёшево масштабировать очередь воркеров | Каждый воркер — процесс браузера, дорого по CPU/RAM при 50+ филиалах |
| Хрупкость | Ломается при смене **формата ответа JSON** или токена авторизации запроса | Ломается при смене **селекторов/вёрстки**, но менее чувствителен к внутренним API |
| Антибот | Проще спалиться (нет полноценной эмуляции браузера/fingerprint) | Ближе к поведению реального пользователя, легче эмулировать скролл |
| Сложность поддержки | Нужно регулярно сверять формат JSON с реальными XHR в DevTools | Не нужно знать формат API, но нужно поддерживать селекторы DOM |

Для задачи «парсить много карточек регулярно» скорость и стоимость
инфраструктуры на масштабе перевешивают: JSON-подход выбран
основным. Playwright оставлен как **запасной путь** ровно на случай, если
антибот-защита ужесточится настолько, что прямые HTTP-запросы систематически
получают `BannedException` — тогда достаточно переключить
`YANDEX_PARSER_STRATEGY`, не трогая остальной код (это и есть смысл
`OrganizationFetcherInterface`).

## Как парсер понимает, что он сломался

Никогда не возвращается «тихая пустота». Три разных типа ошибок:

- **`SourceUnavailableException`** — сетевая ошибка, таймаут, 403/5xx/429.
  Временная — Laravel сам ретраит job с бэкоффом `[10, 60, 300]` сек.
- **`StructureChangedException`** — ответ получен (200 OK), но в нём **нет
  ожидаемых ключей** (`name`, `rating`, `items`, `id` у отзыва и т.д.).
  Это фиксируется явными проверками в `decodeOrFail()` /
  `mapReview()` — не «поймали Exception откуда-то», а осознанно сверяем
  контракт. Такая ошибка **не ретраится** (ретраить бессмысленно, формат не
  изменится сам), а сразу помечает организацию статусом
  `structure_changed`, пишет в лог `debugContext` (какие ключи реально
  пришли) и показывает пользователю понятное сообщение на фронте.
- **`BannedException`** — HTTP 429 или признаки капчи (`SmartCaptcha` в теле
  ответа) — организация помечается `failed`, job откладывается на 5 минут
  (`release(300)`), это не «сломанный парсер», а временная блокировка.

## Постраничная навигация: что грузить, что кэшировать

**Решение: парсим ~600 отзывов один раз (в фоне, при подключении/по
запросу), сохраняем в БД, а страницы 50/50 отдаём из БД** через обычный
`paginate()`. Дергать источник заново на каждый клик «следующая страница»
было бы:
- медленно (пользователь ждёт сотни мс–секунды до Яндекса на каждый клик);
- рискованно для анти-бана (лишние запросы к источнику без необходимости);
- бессмысленно, т.к. отзывы не меняются каждую секунду — раз в
  какое-то время (ручной «Перепарсить» или по расписанию) достаточно.

Единственный сетевой запрос на клик — это запрос к **своему** API
(`GET /reviews?page=N`), лёгкий и быстрый.

## Масштаб и фоновая обработка

Реализовано: каждая организация парсится в отдельном `ParseOrganizationReviewsJob`
через очередь `parsing` (Redis), с `tries=3` и экспоненциальным бэкоффом.
Прогресс (`0–100`) пишется в `organizations.progress` и `parse_jobs.progress`
после каждой обработанной страницы отзывов — фронт получает его через
поллинг `GET /status`.

Для сети из ~50 филиалов это масштабируется горизонтально: несколько
`queue:work` воркеров разбирают очередь параллельно, глобальный
rate-limit (Redis `SET NX PX`, см. `acquireGlobalSlot()`) не даёт им
одновременно долбить Яндекс. При необходимости легко добавить
`php artisan schedule` для регулярного авто-обновления всех подключённых
организаций (например, раз в сутки), не реализовано в рамках тестового —
но архитектурно ничего не мешает.

## Анти-бан на объёме

- **Троттлинг**: пауза между запросами одного воркера (`YANDEX_REQUEST_DELAY_MS`)
  + **глобальный** распределённый лимитер между всеми воркерами через Redis
  (`acquireGlobalSlot()` в job'е) — иначе троттлинг внутри одного процесса
  не спасает при нескольких параллельных воркерах.
- **Бэкофф**: при `BannedException` job не падает молча, а откладывается
  (`release(300)`) — следующая попытка через 5 минут, а не сразу.
- **Ротация User-Agent и прокси**: `YANDEX_USER_AGENT_POOL` / `YANDEX_PROXY_POOL`
  в конфиге, `pickUserAgent()`/`pickProxy()` в `HttpJsonFetcher` берут
  случайный элемент на каждый запрос.
- **Обработка «нас забанили»**: `looksLikeCaptcha()` проверяет тело ответа
  на признаки `SmartCaptcha`, статус 429 тоже трактуется как бан — в обоих
  случаях бросается `BannedException`, а не `SourceUnavailableException`,
  чтобы job вёл себя иначе (более долгая задержка, отдельный лог-канал для
  алертинга «пора менять прокси/паузы»).

## Идемпотентность и история изменений

- Отзывы апсертятся по уникальному ключу `(organization_id, external_id)`
  (`reviews` таблица, `updateOrCreate` в `OrganizationSyncService`) —
  повторный парсинг не создаёт дублей.
- У каждого отзыва хранится `content_hash` (sha256 от автора+текста+
  рейтинга+даты) — если Яндекс отдал тот же `external_id`, но пользователь
  отредактировал отзыв, хэш изменится, и мы это фиксируем как
  `reviews_updated`, а не как «ничего не поменялось».
- После каждого парсинга создаётся строка в `organization_snapshots`
  (агрегаты рейтинга/счётчиков на момент парсинга + `reviews_added`/
  `reviews_updated` за этот прогон) — так можно посмотреть «было → стало»
  между любыми двумя датами парсинга, не реализуя это как отдельный экран
  в рамках тестового (данные для этого уже есть в БД).

## Что не реализовано полностью

- `PlaywrightFetcher` — сейчас это рабочий каркас (интерфейс + вызов
  внешнего Node-скрипта), но сам `resources/scripts/yandex-scrape.mjs` не
  написан — это отдельная задача на пару часов (запуск Playwright,
  эмуляция скролла блока отзывов, извлечение `window.__INITIAL_STATE__`).
- Реальные эндпоинты/поля JSON в `HttpJsonFetcher` — написаны по образу
  того, как устроены подобные SPA-карточки, но не сверены с текущим
  живым Яндексом (нет сети в среде разработки) — при реальном запуске
  первым делом стоит открыть DevTools → Network на живой карточке и
  подставить точные URL/имена полей.
- Экран истории изменений («было → стало» по `organization_snapshots`) —
  данные уже пишутся, но отдельного UI/эндпоинта для просмотра нет.
- `php artisan schedule` для автоматического периодического обновления
  всех подключённых организаций (не только вручную по кнопке).
- Тесты (Pest/PHPUnit) на `UrlValidator`, `OrganizationParser` (с
  фейковым `OrganizationFetcherInterface`) и `OrganizationSyncService` —
  структура кода это позволяет (всё через интерфейсы/DI), но сами тесты
  не написаны из-за нехватки времени в этой сессии.
- Деплой на реальный хостинг — я не могу задеплоить из этой среды
  (нет исходящего доступа к хостинг-провайдерам); нужно будет поднять
  самостоятельно, например, через `docker-compose` на любом VPS, или
  разнести backend на Render/Railway + frontend на Vercel/Netlify.
